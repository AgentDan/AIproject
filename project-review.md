# Резюме проекта: AI Product Scene Platform

*Документ составлен на основе прямого анализа всех исходных файлов проекта.*

---

## 1. Что это за проект

**AI Product Scene Platform** — платформа для управления 3D-сценами и продуктовыми объектами с помощью голосовых или текстовых команд на естественном языке. Идея: пользователь произносит или печатает команду («передвинь объект влево», «покрась в красный», «покажи габариты», «измерь расстояние», «выгрузи сцену»), а платформа распознаёт намерение, формирует план действий и применяет его к сцене.

Проект находится на стадии раннего MVP. Сквозной цикл «команда → ответ» собран и работает, но ключевые компоненты — реальный AI-движок и настоящий 3D-парсер — пока заменены детерминированными заглушками. Архитектура при этом спроектирована так, чтобы подключить их позже без переписывания ядра.

**Версия:** 0.1.0. **Лицензия/тип:** приватный монорепозиторий.

## 2. Описание архитектуры

Проект устроен как **монорепозиторий на npm workspaces** с четырьмя пакетами:

| Пакет | Технологии | Роль |
|---|---|---|
| `packages/contracts` | Vanilla JS (ESM) | Общие контракты данных между всеми этапами |
| `apps/server` | Node.js, встроенный `http` | HTTP API и оркестрация пайплайна |
| `apps/client` | React 19, Vite, Tailwind v4 | Веб-клиент: голос/текст + 3D-превью |
| `apps/mobile` | React Native, Expo | Мобильное приложение |

### Сквозной поток обработки команды

```
Пользователь (голос/текст)
  → Client → POST /api/commands
  → Валидация ClientRequest
  → Запись запроса в локальное хранилище
  → buildSceneContext()      — сборка контекста сцены
  → runAiServicesPipeline()  — распознавание намерения → ActionPlan
  → executeSceneModulesPipeline() — исполнение плана → SceneResult
  → ClientResponse → обновление превью на клиенте
```

**Ключевой архитектурный принцип:** AI-сервисы не изменяют сцену напрямую. Они порождают `ActionPlan` (структурированный план). Модули сцены исполняют этот план, проверяют результат и возвращают `SceneResult`. Это чистое разделение «планировщик / исполнитель».

### Контракты данных (`packages/contracts`)

Пять контрактов, каждый с фабрикой `create*` и валидатором `validate*`:

- **ClientRequest** — вход от клиента (команда, тип ввода, sessionId, sceneId).
- **SceneContext** — состояние сцены, передаётся в AI-сервисы.
- **ActionPlan** — выход AI: упорядоченные шаги (тип, цель, параметры).
- **SceneResult** — итог исполнения (статус, diff, измерения, валидация).
- **ClientResponse** — ответ клиенту.

### AI-сервисы (`apps/server/src/ai-services`)

Конвейер: `buildPrompt → detectIntent → processSceneUnderstanding → generateActionPlan → parseAiResponse → validateGeneratedActionPlan → (fallback при ошибке)`.

Распознавание намерений — **regex-сопоставление по ключевым словам**. Поддерживается 5 типов действий: `move_object`, `change_object_color`, `show_bounding_boxes`, `measure_mesh_distance`, `download_updated_scene`. При несовпадении конвейер по умолчанию выбирает `move_object` с уверенностью 0.42. Направление сдвига и цвет также выводятся из ключевых слов команды.

### Модули сцены (`apps/server/src/scene-modules`)

Конвейер: `createSceneGraph → executeStep (×N) → validateSceneState → generateSceneDiff → createExportReference`. Каждый шаг проходит проверку product-rules, затем применяется transform-, material- или mesh-движок. Результат — `SceneResult` с превью-обновлением и диффом.

### Хранилище (`apps/server/src/storage`)

Локальное JSON-хранилище в `apps/server/data/`: каталоги `sessions/`, `scenes/`, `action-history/`, `assets/`, `exports/`. Каждая сессия/сцена — отдельный JSON-файл. Корень переопределяется переменной `SERVER_STORAGE_DIR`.

## 3. Текущее состояние (как есть сейчас)

Что **реально работает**:

- Полный HTTP-цикл «запрос → ответ» через `POST /api/commands`.
- Распознавание речи в браузере через Web Speech API с текстовым фолбэком.
- Детектирование 5 намерений по ключевым словам и генерация валидного `ActionPlan`.
- Исполнение плана: сдвиг позиции и смена цвета объекта в графе сцены.
- Подсчёт диффа сцены и сохранение сессий/истории в JSON.
- Полноэкранный клиент с плавающей панелью команд и авто-исчезающим уведомлением.

Что является **заглушкой**:

- `buildPrompt` формирует промпт, но он **никуда не отправляется** — LLM-вызова нет.
- `parseAiResponse` — пустой проброс объекта (не парсит ничего реального).
- Сцена всегда состоит из **одного объекта по умолчанию** (`preview-product`) — реального GLB/GLTF-парсинга нет.
- `createExportReference` возвращает строку-ссылку `local://exports/...glb`, файл не создаётся.
- Измерение расстояния (`measure_mesh_distance`) всегда даёт 0, т.к. в сцене один объект.
- Мобильное приложение — игра «лови бабочек», не связанная с платформой.
- Каталоги `apps/server/src/api/` и `.../validation/` пусты (только `.keep.md`) — фактически логика API и валидации лежит в `index.js`.

## 4. Сильные стороны

1. **Чистая, расширяемая архитектура.** Разделение «AI-планировщик / исполнитель сцены» — правильное решение. Замена regex на LLM или заглушки сцены на реальный 3D-движок не потребует переписывания оркестратора в `index.js`.

2. **Контракты данных как граница ответственности.** Пакет `contracts` фиксирует формат на каждом стыке пайплайна и даёт валидацию. Это одновременно документация и защита от рассинхронизации модулей.

3. **Дисциплина валидации.** Сервер проверяет результат на каждом этапе (ClientRequest → SceneContext → ActionPlan → SceneResult) и возвращает осмысленные ошибки. Есть fallback-план на случай провала валидации.

4. **Рабочий end-to-end уже на MVP.** Есть живой сценарий, который можно показывать и тестировать с первого дня.

5. **Голосовой ввод без внешних зависимостей.** Web Speech API в браузере — разумный выбор для MVP, не требует серверной транскрипции.

6. **Аккуратный, единообразный код.** Маленькие функции, чистый ESM, предсказуемый стиль во всех модулях.

---

## 5. Слабые стороны

1. **«AI» отсутствует.** Ядро ценности продукта — понимание естественного языка — реализовано через regex. Любая команда вне 5 шаблонов молча трактуется как «передвинуть объект». Промпт строится, но не используется.

2. **Нет реальной 3D-сцены.** Сервер всегда работает с одним синтетическим объектом. Нет загрузки и мутации GLB/GLTF, экспорт — фиктивная строка. Часть функций (`measure_mesh_distance`) поэтому бессмысленна на текущих данных.

3. **Полное отсутствие тестов.** Ни одного автотеста при пайплайне из ~15 модулей. Любой рефакторинг рискован, регрессии не отлавливаются.

4. **Хрупкое хранилище.** JSON-файлы без транзакций и блокировок. `appendActionHistory` делает read-modify-write — при параллельных запросах возможна потеря записей. Не масштабируется.

5. **Сервер без фреймворка.** Голый `http`-сервер: маршрутизация через цепочку `if`, тело запроса парсится вручную. Добавление middleware (авторизация, rate limiting, логирование) потребует велосипедов.

6. **Расхождение плана и реализации.** Пустые каталоги `api/` и `validation/` намекают на задуманную структуру, которой код не следует. Архитектурная документация (`readme.md`) удалена — проект потерял описание.

7. **Клиент не показывает большую часть результата.** Превью отображает только позицию X/Y и цвет первого объекта. Ось Z, поворот, масштаб, габаритные рамки и измерения вычисляются на сервере, но никак не визуализируются.

8. **Мобильное приложение — посторонний код.** Игра про бабочек не имеет отношения к платформе и создаёт разрыв между заявленным и реальным.

9. **Мелкие несоответствия.** Успешный ответ отдаётся как HTTP `202 Accepted`, хотя обработка синхронная и завершённая (корректнее `200`). CORS открыт настежь (`*`). Нет `.env.example`.

## 6. Рекомендации

### Приоритет 1 — Подключить настоящий LLM
Без этого продукт не имеет смысла. Архитектура готова: достаточно заменить `intent-detector.js` и `action-plan-generator.js` на вызов Claude API (Anthropic) или OpenAI с использованием structured output / tool use для получения `ActionPlan` в нужном формате. Уже формируемый `buildPrompt` — естественная точка интеграции.

### Приоритет 2 — Реальная 3D-сцена
На клиенте — Three.js или Babylon.js для рендеринга. На сервере — `@gltf-transform/core` для загрузки и мутации GLB. После этого `gltf-glb-exporter.js` начнёт создавать настоящие файлы, а `scene-context-builder.js` — собирать сцену из реальных данных.

### Приоритет 3 — Базовое покрытие тестами
Начать с unit-тестов на `contracts` и AI-сервисы (Vitest — минимальная настройка для ESM). Добавить хотя бы один smoke-тест на `POST /api/commands`. Это снимет основной риск рефакторинга.

### Приоритет 4 — HTTP-фреймворк
Заменить голый `http` на лёгкий ESM-нативный фреймворк (Hono или Fastify): получите маршрутизацию, middleware и валидацию схем малой ценой. Заодно сузить CORS до конкретного origin клиента.

### Приоритет 5 — Достроить клиент и мобильное приложение
Визуализировать на клиенте весь `SceneResult` (поворот, масштаб, габаритные рамки, измерения). Подключить мобильное приложение к тому же `/api/commands` и убрать постороннюю игру.

### Долгосрочно
- Заменить JSON-хранилище на PostgreSQL (сессии, история) + S3 (GLB-файлы).
- Добавить авторизацию и идентификацию сессий.
- Рассмотреть переход `server` и `contracts` на TypeScript — контракты данных особенно выиграют от строгой типизации.
- Восстановить и поддерживать архитектурную документацию (`readme.md` был удалён).

## 7. Итог

Проект имеет **сильную архитектурную основу и верное продуктовое видение**: разделение планировщика и исполнителя, типизированные контракты, дисциплина валидации, монорепо с чистыми границами. Главная проблема — **разрыв между архитектурой и реализацией**: ключевые компоненты (LLM, 3D-движок, хранилище) заменены заглушками, тесты отсутствуют, мобильная часть не относится к продукту.

Это нормальное состояние для раннего MVP, и каркас выбран грамотно. Ближайший шаг, дающий максимальную отдачу, — подключить Claude/OpenAI и реальный 3D-движок: после этого платформа начнёт демонстрировать заявленную ценность, а не имитировать её.
